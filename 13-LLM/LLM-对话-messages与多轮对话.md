# messages 与多轮对话：上一轮的数据是怎么发出去的

## 一、先解答最核心的疑问

很多人第一次写多轮对话都会卡在同一个问题：

> 第一轮我问了，模型答了；第二轮我怎么让模型"记得"第一轮？

答案是：**你不发，它就不知道**。Chat Completions 是**无状态接口**，服务端不保存任何会话。所谓"上下文"，是你每次请求时把历史**原样重新发一遍**造出来的。

```
第 1 轮请求： [user: Q1]
第 2 轮请求： [user: Q1] [assistant: A1] [user: Q2]   ← 历史全部重发
第 3 轮请求： [user: Q1] [assistant: A1] [user: Q2] [assistant: A2] [user: Q3]
```

服务端看到的永远是"一段完整对话记录"，它并不知道你之前单独发过几次请求。**"会话"是客户端自己维护出来的概念**，服务端没有 session、没有 conversation_id 这种东西。

## 二、messages 的结构

`messages` 是一个**数组**，每个元素是一条消息，最少两个字段：

```json
{ "role": "user", "content": "帮我整理今天的会议" }
```

- `role`：谁在说话
- `content`：说了什么

**数组顺序就是时间顺序**，模型按这个顺序读，不会自己去猜哪句早哪句晚。

## 三、四种常见 role

| role | 谁写的 | 作用 | 能否省略 |
|---|---|---|---|
| `system` | 开发者 | 设定身份、规则、输出格式、术语表 | 可省，但强烈建议写 |
| `user` | 用户 / 程序 | 提问、给材料、贴日志 | 必须有，且通常最后一条 |
| `assistant` | 模型 | 模型的回复，包括历史里的旧回复 | 多轮时必须回填 |
| `tool` | 工具执行结果 | 工具调用的返回值，紧跟对应的 `assistant` 消息 | 只有用了工具才出现 |

`system` 是"总纲"，位置必须在最前。它的内容会以最高优先级影响输出风格，但也**不是硬约束**——真要保证格式，还是得靠 `response_format` 的 schema。

部分新接口（如 OpenAI 的 Responses / 新版 Chat）还引入了 `developer` role，作用等同旧版 `system`，百炼的兼容模式下按 `system` 用即可。

## 四、content 不止是字符串

纯文本时 `content` 是字符串：

```json
{ "role": "user", "content": "这段话说了什么？" }
```

要带图片、音频时，`content` 变成一个**数组**，每项是一块内容：

```json
{
  "role": "user",
  "content": [
    { "type": "text", "text": "这张图里的报错是什么原因？" },
    { "type": "image_url", "image_url": { "url": "https://example.com/err.png" } }
  ]
}
```

也可以直接塞 base64（`data:image/png;base64,...`），但请求体会变得很大，长对话下不建议。图、音、视最终都被编码成 token，仍然按 token 计费（音频每秒 25 token）。

## 五、上一轮的数据怎么发：两种写法

### 写法 A：手动维护一个 list

```python
import os, json
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DASHSCOPE_API_KEY"],
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",
)

history = [{"role": "system", "content": "你是会议纪要助手，回答简洁。"}]

while True:
    q = input("你：")
    if q in ("exit", "quit"):
        break

    history.append({"role": "user", "content": q})

    resp = client.chat.completions.create(
        model="qwen3.8-flash",
        messages=history,          # ← 全量历史，每次重发
    )

    answer = resp.choices[0].message.content
    print("模型：" + answer)

    # 关键：把模型的回复原样回填进历史，否则下一轮它就"失忆"
    history.append({"role": "assistant", "content": answer})
```

### 写法 B：直接 append 返回的消息对象

OpenAI SDK 返回的 `message` 本身就是合法的消息结构，可以直接塞回列表：

```python
history.append(resp.choices[0].message)   # 不用手工拆 content
```

两种写法等价，B 更省事，但如果要把历史存盘（比如写 json 文件），A 更可控——`message` 是 pydantic 对象，需要 `.model_dump()` 才能序列化。

## 六、两轮对话，请求体实际长什么样

### 第 1 次请求

```json
{
  "model": "qwen3.8-flash",
  "messages": [
    { "role": "system", "content": "你是会议纪要助手，回答简洁。" },
    { "role": "user", "content": "帮我整理：B 负责测试，周五前给结论。" }
  ]
}
```

### 第 2 次请求（用户接着问"那谁负责上线？"）

```json
{
  "model": "qwen3.8-flash",
  "messages": [
    { "role": "system", "content": "你是会议纪要助手，回答简洁。" },
    { "role": "user", "content": "帮我整理：B 负责测试，周五前给结论。" },
    { "role": "assistant", "content": "测试由 B 负责，结论周五前给出。" },
    { "role": "user", "content": "那谁负责上线？" }
  ]
}
```

对比一下就能看出来：**前三项和第 1 次请求完全一样，只是在尾部追加了两项**。这个"前缀完全相同"的特征很重要，下一节讲它带来的成本影响。

## 七、无状态设计的两个好处

### 1. 可重放、可并行

同一个请求发两次，结果（在 temperature=0 时）基本一致。服务端不用维护成千上万的 session，扩容时不用做 session 迁移。

### 2. 前缀缓存天然可命中

历史是**逐轮增长的前缀**：第 3 次请求的前 N 项，和第 2 次请求一模一样。所以服务端的前缀缓存能直接复用这部分的 KV 张量。

```
第 2 次： [sys][Q1][A1][Q2]              ← 前 4 项被缓存
第 3 次： [sys][Q1][A1][Q2][A2][Q3]      ← 前 4 项命中，只算后 2 项
```

这就是为什么多轮对话的输入费用不会完全按 O(n²) 涨——命中部分打了很大折扣（命中价常是未命中的 1/10 甚至更低）。

**但前提是前缀一个字都不能变**。如果每次都在 system prompt 里塞当前时间、会话 id，或者把历史重排（摘要放前面、原话放后面），缓存立刻失效，费用按全价算。

## 八、历史的成本是平方级增长

假设每轮问答各 1000 token：

| 轮次 | 本次输入 token | 累计输入 token |
|---|---|---|
| 1 | 1000 | 1000 |
| 2 | 2000 | 3000 |
| 3 | 3000 | 6000 |
| 10 | 10000 | 55000 |
| 30 | 30000 | 465000 |

30 轮对话，累计输入是单轮的上千倍。如果不做历史管理，长会话的账单会非常难看，而且最终会撞到模型的上下文上限（超出直接报错或截断）。

> 上下文上限具体是多少、由谁决定、超了会怎样、显存怎么算，见 [上下文窗口](./LLM-上下文-窗口与上限.md)。

## 九、历史管理的四种策略

| 策略 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 滑动窗口 | 只保留最近 N 轮 | 实现最简单 | 早期信息丢失 |
| 摘要压缩 | 把旧历史交给模型总结成一段 | 保留关键信息，token 大降 | 多一次调用，可能丢细节 |
| 关键信息抽取 | 只留实体、结论、待办 | 最省 | 依赖抽取质量 |
| 检索式 | 历史存外部，每次按需召回相关片段 | 理论最优 | 工程复杂，需要向量库 |

会议纪要这类场景，最实用的组合是**滑动窗口 + 摘要**：保留最近 3~5 轮原话，更早的压成一段"前情提要"放在 system 后面。

注意顺序：摘要要放在**历史区的最前面**（紧跟 system），因为它比逐轮原话更"稳定"，这样才有机会吃缓存；如果每轮都重新生成摘要，那这段就每次都是新的，等于每次都全价。

> 预算怎么切、什么时候触发压缩、归档与分层摘要怎么写，见 [长会话的上下文管理](./LLM-上下文-长会话管理.md)。

## 十、踩坑清单

1. **忘了回填 assistant** —— 最典型。下一轮模型完全不知道上一轮说了什么，表现得像"失忆"。必须把 `resp.choices[0].message.content` 原样放进历史。
2. **改写了 assistant 的内容** —— 有人喜欢把模型回复"润色"再放进历史。模型看到的是你改写后的版本，后续推理会跟着偏。要改就改展示，别改历史。
3. **role 顺序错乱** —— 连续两条 `user` 在某些实现里会被合并，有些会报错。标准节奏是 user / assistant 交替。
4. **tool 消息没有配对** —— 用了工具时，`assistant` 的 `tool_calls` 和后续 `tool` 消息的 `tool_call_id` 必须成对出现，缺一个直接 400。
5. **system 塞了易变内容** —— 时间戳、随机数、请求 id 放开头，缓存全废。
6. **把中间结果当历史** —— 比如把一次失败的重试结果也塞进去，模型会以为那是对的话。
7. **长历史不截断** —— 撞上限后报错，错误信息通常只是"context length exceeded"，看不出是哪段太长。
8. **以为服务端存了会话** —— 换个进程、重启程序，"记忆"就没了，因为记忆一直在你本地那个 list 里。

## 十一、一句话总结

多轮对话的本质是：**你在本地维护一份完整对话记录，每次请求把整份记录重新发出去，模型的"记忆"完全由这份记录构成。**
