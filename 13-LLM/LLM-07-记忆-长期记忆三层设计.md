# 长期记忆的三层设计

## 一、问题：为什么窗口满了还能"记得"

上下文窗口是有限的，按前面的做法，超出就得归档、压缩。那为什么成熟的对话产品能记住几周前的一次闲聊？

因为它不靠窗口，靠**窗口外面的一套记忆结构**。这套结构通常是三层。

## 二、三层结构

| 层次 | 存什么 | 存在哪 | 生命周期 |
|---|---|---|---|
| L1 本次窗口 | 最近若干轮**原文** | 请求体里的 `messages` | 一次请求 |
| L2 摘要 | 较早对话的**压缩要点** | 本地数据库 / 文件 | 天~月 |
| L3 结构化档案 | 稳定事实，拆成**字段条目** | KV / 表 / JSON | 长期，直到被覆盖 |

三层的分工不是"备份"，而是**压缩率不同**：

```
原文 1000 字  ──压成──▶  摘要 100 字  ──再抽──▶  档案 1 条 "职业=嵌入式工程师"
```

越往下越省空间、越经久，但细节损失越多。所以三层必须同时在，不能只留最下面一层——只剩档案就会变成"知道你叫什么，但不知道上次聊到哪"。

## 三、为什么用户感觉像"真记得"

因为模型每次只看到被拼好的输入，它不知道哪些来自窗口、哪些来自档案。只要拼装结果信息量够，表现出来就是"记忆连贯"。

这带来一个重要结论：**记忆质量取决于拼装策略，而不是模型大小**。同样一个模型，材料选得好就显得聪明，选得差就显得失忆。

## 四、真正的难点：这一刻该想起哪几条

存不是问题，取才是问题。取错了比忘了更糟——模型会一本正经地用 A 事的前提回答 B 事。

常见的取法，从简到繁：

| 取法 | 实现 | 适用 |
|---|---|---|
| 全量注入 | 档案全部塞进 system | 条目少（几十条）时最省事 |
| 关键词召回 | 用当前问题 grep 归档文件 | 本地、零依赖、够用 |
| 时间衰减 | 近期的权重高，旧的自然淘汰 | 陪伴类、日常对话 |
| 向量召回 | 语义相似度检索片段 | 归档量大、话题跨度大 |
| 混合 | 关键词 + 向量 + 时效打分 | 生产环境 |

**别一上来就上向量库**。条目在一两百条以内时，全量注入 + 关键词召回往往又快又准，还能完全看清取到了什么。

## 五、写什么、不写什么

记忆系统最容易被搞坏的地方在于写得太多，取不回来反而只是次要问题。判断标准是"**跨任务可复用**"：

| 该记 | 不该记 |
|---|---|
| 身份、职业、技术栈 | 单次任务的发起和取消 |
| 长期约束（不放 C 盘、路径固定） | 一次性指令（"帮我建个定时任务"） |
| 反复被纠正的偏好 | 临时上下文（"这次用 HTML 推给我"） |
| 稳定的项目与环境 | 未经确认的推测 |

原则：**记"人是什么样的"，不记"这次做了什么"**。后者属于任务状态，应该走归档，不该进档案。

## 六、冲突怎么处理

偏好会变。用户昨天说"回复用中文"，今天说"以后都用英文"。

正确做法是**覆盖 + 留痕**，而不是追加：

```
旧: 回复用中文      → 状态: 停用（保留可审计）
新: 回复用英文      → 状态: 生效
```

如果只是追加，"用中文"和"用英文"两条同时生效，模型会随机听一条，表现成"时好时坏"——这种故障极难查，因为它不是每次都复现。

## 七、最小可落地方案

两个文件就能起步，不需要任何数据库：

```
memory/
├─ profile.md      # 稳定事实，条目化，几十条
└─ archive/        
   ├─ 2026-11-20.md
   └─ 2026-11-26.md
```

每次发请求时：

1. 读 `profile.md`，压到 300 字以内，放进 system 或第一条 user 消息
2. 按当前话题从 `archive/` 里 grep 出 1~2 段相关原文，作为"参考资料"追加
3. 拼接最近 N 轮原话 + 新问题
4. 对话结束后，把本轮原文追加进当天的归档文件（**只增不改**）

`profile.md` 的建议格式——短、陈述句、一条一行，方便全量注入：

```markdown
- 嵌入式开发工程师，技术栈 C / Python / RK3568 / STM32
- 工作文件优先放 D 盘，避免占用 C 盘
- 回复用简体中文，代码注释中文、打印输出英文
- 讲解技术点时先讲问题背景再引出知识点
```

## 八、和结构化输出的配合

档案的抽取值得用一次 `json_schema` 调用，而不是让模型自由发挥：

```json
{
  "type": "object",
  "properties": {
    "facts": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "content": { "type": "string" },
          "scope": { "type": "string", "enum": ["profile", "task"] },
          "confidence": { "type": "number" }
        },
        "required": ["content", "scope", "confidence"],
        "additionalProperties": false
      }
    }
  },
  "required": ["facts"],
  "additionalProperties": false
}
```

`scope` 字段是关键：抽出来是 `task` 的就丢掉，只把 `profile` 的写进档案。这一步能挡掉大部分"记了一堆一次性指令"的垃圾。

## 九、失败模式清单

| 现象 | 病因 |
|---|---|
| 记得很多但总用不上 | 只存不取，或取法太粗 |
| 时而记得时而忘 | 冲突条目没覆盖，两条同时生效 |
| 记了一堆没用的 | 写入策略缺失，把任务指令当事实 |
| 拿 A 事的前提答 B 事 | 召回不准，且没有相关性门槛 |
| 越用越慢、越用越贵 | 全量注入条目无限增长，没有淘汰机制 |

## 十、一句话结论

**记忆 = 分层压缩 + 按需召回 + 严格的写入标准。** 模型本身永远无状态，所谓"记得"，是每次请求时你递给它的那几张纸选得好。
