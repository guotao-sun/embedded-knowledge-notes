# 长期记忆的三层设计

## 一、问题：为什么窗口满了还能"记得"

上下文窗口是有限的，按前面的做法，超出就得归档、压缩。那为什么成熟的对话产品能记住几周前的一次闲聊？

因为它不靠窗口，靠**窗口外面的一套记忆结构**。这套结构通常是三层。

## 二、三层结构

| 层次 | 存什么 | 存在哪 | 生命周期 |
|---|---|---|---|
| L1 本次窗口 | 最近若干轮**原文** | 请求体里的 `messages` | 一次请求 |
| L2 摘要 | 较早对话的**压缩要点** | 本地数据库 / 文件 | 天~月 |
| L3 结构化档案 | 稳定事实，拆成**字段条目** | KV / 表 / JSON | 长期，直到被覆盖 |

三层的分工不是"备份"，而是**压缩率不同**：

```
原文 1000 字  ──压成──▶  摘要 100 字  ──再抽──▶  档案 1 条 "职业=嵌入式工程师"
```

越往下越省空间、越经久，但细节损失越多。所以三层必须同时在，不能只留最下面一层——只剩档案就会变成"知道你叫什么，但不知道上次聊到哪"。

## 三、为什么用户感觉像"真记得"

因为模型每次只看到被拼好的输入，它不知道哪些来自窗口、哪些来自档案。只要拼装结果信息量够，表现出来就是"记忆连贯"。

这带来一个重要结论：**记忆质量取决于拼装策略，而不是模型大小**。同样一个模型，材料选得好就显得聪明，选得差就显得失忆。

## 四、真正的难点：这一刻该想起哪几条

存不是问题，取才是问题。取错了比忘了更糟——模型会一本正经地用 A 事的前提回答 B 事。

常见的取法，从简到繁：

| 取法 | 实现 | 适用 |
|---|---|---|
| 全量注入 | 档案全部塞进 system | 条目少（几十条）时最省事 |
| 关键词召回 | 用当前问题 grep 归档文件 | 本地、零依赖、够用 |
| 时间衰减 | 近期的权重高，旧的自然淘汰 | 陪伴类、日常对话 |
| 向量召回 | 语义相似度检索片段 | 归档量大、话题跨度大 |
| 混合 | 关键词 + 向量 + 时效打分 | 生产环境 |

**别一上来就上向量库**。条目在一两百条以内时，全量注入 + 关键词召回往往又快又准，还能完全看清取到了什么。

## 五、写什么、不写什么

记忆系统最容易被搞坏的地方在于写得太多，取不回来反而只是次要问题。判断标准是"**跨任务可复用**"：

| 该记 | 不该记 |
|---|---|
| 身份、职业、技术栈 | 单次任务的发起和取消 |
| 长期约束（不放 C 盘、路径固定） | 一次性指令（"帮我建个定时任务"） |
| 反复被纠正的偏好 | 临时上下文（"这次用 HTML 推给我"） |
| 稳定的项目与环境 | 未经确认的推测 |

原则：**记"人是什么样的"，不记"这次做了什么"**。后者属于任务状态，应该走归档，不该进档案。

## 六、冲突怎么处理

偏好会变。用户昨天说"回复用中文"，今天说"以后都用英文"。

正确做法是**覆盖 + 留痕**，而不是追加：

```
旧: 回复用中文      → 状态: 停用（保留可审计）
新: 回复用英文      → 状态: 生效
```

如果只是追加，"用中文"和"用英文"两条同时生效，模型会随机听一条，表现成"时好时坏"——这种故障极难查，因为它不是每次都复现。

## 七、最小可落地方案

两个文件就能起步，不需要任何数据库：

```
memory/
├─ profile.md      # 稳定事实，条目化，几十条
└─ archive/        
   ├─ 2026-11-20.md
   └─ 2026-11-26.md
```

每次发请求时：

1. 读 `profile.md`，压到 300 字以内，放进 system 或第一条 user 消息
2. 按当前话题从 `archive/` 里 grep 出 1~2 段相关原文，作为"参考资料"追加
3. 拼接最近 N 轮原话 + 新问题
4. 对话结束后，把本轮原文追加进当天的归档文件（**只增不改**）

`profile.md` 的建议格式——短、陈述句、一条一行，方便全量注入：

```markdown
- 嵌入式开发工程师，技术栈 C / Python / RK3568 / STM32
- 工作文件优先放 D 盘，避免占用 C 盘
- 回复用简体中文，代码注释中文、打印输出英文
- 讲解技术点时先讲问题背景再引出知识点
```

## 八、和结构化输出的配合

档案的抽取值得用一次 `json_schema` 调用，而不是让模型自由发挥：

```json
{
  "type": "object",
  "properties": {
    "facts": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "content": { "type": "string" },
          "scope": { "type": "string", "enum": ["profile", "task"] },
          "confidence": { "type": "number" }
        },
        "required": ["content", "scope", "confidence"],
        "additionalProperties": false
      }
    }
  },
  "required": ["facts"],
  "additionalProperties": false
}
```

`scope` 字段是关键：抽出来是 `task` 的就丢掉，只把 `profile` 的写进档案。这一步能挡掉大部分"记了一堆一次性指令"的垃圾。

## 九、失败模式清单

| 现象 | 病因 |
|---|---|
| 记得很多但总用不上 | 只存不取，或取法太粗 |
| 时而记得时而忘 | 冲突条目没覆盖，两条同时生效 |
| 记了一堆没用的 | 写入策略缺失，把任务指令当事实 |
| 拿 A 事的前提答 B 事 | 召回不准，且没有相关性门槛 |
| 越用越慢、越用越贵 | 全量注入条目无限增长，没有淘汰机制 |

## 十、一句话结论

**记忆 = 分层压缩 + 按需召回 + 严格的写入标准。** 模型本身永远无状态，所谓"记得"，是每次请求时你递给它的那几张纸选得好。

## 十一、落地实现与实测（2026-11-26）

上面是设计，下面是把它真跑起来之后暴露的东西。实现是一份纯标准库单文件脚本（`urllib` 手拼 HTTP，不装 SDK）+ 一份配置文件，跑在 `qwen3.8-flash` 上。

### 11.1 归档文件长什么样（L2）

按天一个文件，每轮一块，**只增不改**：

```markdown
### 10:31:07 [turn 1]
- user: 我是嵌入式工程师，主要用 C 和 Python，做 RK3568 平台，文件习惯放 D 盘
- assistant: 记住了。……

### 10:31:52 [turn 2]
- user: 板子上的烧录流程再讲一遍
- assistant: ……
```

带 `[turn N]` 是为了召回时能判断"这段是第几轮、前后还聊了什么"，光有正文很难定位。

### 11.2 召回：中文别用 grep，也别用 Jaccard

笔记第七节说"grep 出 1~2 段相关原文"。真跑起来第一个卡点就是它：**中文没有空格**。

- `grep RK3568` 能中，因为英文术语是连续字符；
- `grep 板子怎么烧录` 一条都中不了，因为归档里写的是"RK3568 的烧录流程"——中间隔了词。

按空格切词这条路在中文上直接废掉。所以改成**字符二元组**（每相邻两个字算一个单元）：

```
查询 "RK3568 烧录"  →  {"RK", "K3", "35", "56", "68", "烧录"} 之类
归档块             →  同样切成一堆二元组
score = |查询二元组 ∩ 归档二元组| / |查询二元组|
```

**分母只算查询，不算归档块**——这是第二个坑。第一版用的是 Jaccard（交集除以并集），结果长归档块会把分数稀释到 0.0x，永远过不了阈值：实测 `/recall RK3568` 完全 miss，明明那段就是讲 RK3568 的。改成"查询被覆盖了多少"之后，同样这句直接 1.00。

改完的实测：

| 查询 | 分数 | 是否召回 |
|---|---|---|
| `RK3568` | 1.00 | 命中 |
| `D盘` / `C盘` | 1.00 | 命中 |
| `今天天气` | ≈0 | 不召 |

阈值定在 **0.35**（0.12 太松，无关问题也会被拽出一段）。还有一个隐蔽 bug：早期代码遇到"整块超过 `RECALL_MAX_CHARS`"就**跳过整块**，导致长对话永远召不回。正确做法是**超预算截断**，尾部标 `…(truncated)`，宁可少给也不能不给。

### 11.3 档案条目字段（L3）

```json
{
  "id": "p5",
  "content": "主力技术栈：C / Python / RK3568",
  "topic": "技术栈",
  "scope": "profile",
  "confidence": 0.95,
  "status": "active",
  "created_at": "2026-11-26T10:31:07",
  "updated_at": "2026-11-26T10:37:20",
  "source": "turn 2",
  "replaces": ["p2"]
}
```

被覆盖的那条不删，改状态并留痕：

```json
{"id": "p2", "status": "inactive", "deactivated_at": "…", "deactivated_by": "p5"}
```

同时生成一份 `profile.md` 人读镜像（生效一段、停用一段），几百条以内直接打开就能看懂系统记得什么——这比查数据库有用得多，调 prompt 时全靠它。

### 11.4 冲突判定只能靠 topic —— 这一节是重点

笔记第六节说"覆盖 + 留痕"，但没回答一个实现问题：**两条事实凭什么算"同一条"？**

模型的输出是自然语言，同一件事每次措辞都不一样：

```
第 1 轮: "主力使用 C 和 Python"
第 3 轮: "技术栈是 C/Python，另外加了 RK3568"
```

字符串比对必然不相等，按内容相似度算阈值又没法调。所以必须在 **schema 里加一个稳定标号**：

```json
{"content": {"type": "string"},
 "topic":   {"type": "string", "description": "2~4 字的稳定分类名，如 职业 / 技术栈 / 文件习惯"},
 "scope":   {"type": "string", "enum": ["profile", "task"]},
 "confidence": {"type": "number"}}
```

判定规则变成一句话：**`topic` 相同即视为同一主题，新条目覆盖旧条目。**

这带来一个必须接受的代价：**冲突检测的准确性，等于模型每次给 `topic` 命名的一致性。** 具体会这样坏：

| 第 1 轮 topic | 第 3 轮 topic | 结果 |
|---|---|---|
| 技术栈 | 技术栈 | 覆盖，旧的停用，正确 |
| 技术栈 | 技能栈 | 认为是两条不同事实，**都生效**，模型随机信一条 |
| 技术栈 | （手工 `/profile add` 没写 topic） | 同上，两条并存 |

第二种就是笔记第九节那个"时而记得时而忘"的成因：档案里同时躺着"主力用 C/Python"和"主力用 Rust"，每轮注入时两条都在，模型这次信 A 下次信 B，而且不是每次复现——极难查。

三种缓解手段，按性价比排：

1. **在 `topic` 的 `description` 里约束命名**：写死 2~4 字、复用已有分类。实测模型多数情况会照做，但不能保证。
2. **注入档案时把已有 topic 列表一起回给抽取请求**："已有分类：职业 / 技术栈 / 文件习惯，优先复用"。命中率明显提升，成本是每次抽取多几十个 token。
3. **给"没 topic"的条目兜底**：手工添加必须写成 `/profile add 主题|内容`，不带主题的条目永远不参与覆盖判定（它没有可比对的键）。

另外，`topic` 不必是封闭集合——用 `enum` 写死分类反而会漏掉新维度，用 string + description 引导更实际。

### 11.5 注入位置：档案进 system，召回片段进本轮 user

```text
messages = [
  {system: 基础提示词 + 【长期档案】(压到 300 字)},
  ……最近 N 轮原文……
  {user: 【历史片段参考】…【本轮问题】…}
]
```

召回片段**只拼进当轮 user、不写进 history**。理由很实在：它每轮都可能变，一旦进了 history，后面每轮都要重发一遍这段无关原文，prompt token 白涨，还会让模型把两轮前的"参考资料"当成本轮指令。

档案放 system 也有代价：**档案一变，`system` 前缀就变，prompt 缓存全失效**。档案稳定时缓存命中率高，一天改三五次就无所谓，每轮都改（比如把对话摘要也塞进去）就别指望缓存了。

### 11.6 成本

| 项 | 量级 |
|---|---|
| 每轮对话 | 输入 = system + 档案 + N 轮历史，输出视长度 |
| 每轮抽取 | 额外一次请求，约 300~500 token |
| 思考模型 | `qwen3.8-flash` 每次还会带 50~150 个 `reasoning_tokens` |

抽取成本跟对话本身同量级，聊得短的时候甚至更贵。所以要有 `/extract on|off`，批量灌数据时关掉、平时开着。

### 11.7 仍然没解决的

- **召回没有语义**。问"板子怎么烧录"召不回"RK3568 烧录流程"——二元组不重合。要语义就得向量，属第四节"别一上来就上"的那档，条目上万再考虑。
- **L2 只有归档，没有摘要**。笔记里的 L2 本该是"压缩要点"，实现里只做了原文追加 + 召回，等于把压缩这一步跳过了。会话长到几千轮时，归档检索会变成主要延迟来源。
- **档案没有容量上限**。现在靠 `topic` 覆盖自然收敛，但维度不断新增（职业 + 技术栈 + 习惯 + 项目 + 健康……）迟早撑满 system 那 300 字。需要一个"按更新时间和引用次数打分淘汰"的机制。
- **跨会话不区分**。所有会话共用一份档案。真要分"工作 / 个人"，得在条目上加 `scope_id`，并把召回限定在同组内。
