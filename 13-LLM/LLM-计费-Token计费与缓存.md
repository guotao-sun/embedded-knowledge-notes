# Token 计费与缓存

## 一、费用到底怎么算

### 三档计费

现在主流平台都把输入分成两档、输出一档：

| 档位 | 含义 | 典型价格关系 |
|---|---|---|
| 缓存命中（cache hit） | 输入里和上次完全相同的前缀部分 | 最便宜，常是未命中的 1/10~1/50 |
| 缓存未命中（cache miss） | 输入里的新内容 | 标准输入价 |
| 输出（completion） | 模型生成的字 | 最贵，通常是输入的 3~4 倍 |

以 `qwen3.8-max` 为例（北京地域，价格随时会变，以官网为准）：

| 项目 | 价格（元/百万 token） |
|---|---|
| 输入（未命中） | 12 |
| 输出 | 36 |
| 缓存命中 | 1.5 |
| 显式缓存创建 | 15 |
| 显式缓存命中 | 1 |

同一家的 `qwen3.8-flash` 是 0.8 / 2.7，大约便宜 15 倍。**选型时先想清楚"这次整理值不值得用旗舰"**，日常批量用 flash 就够。

## 二、缓存是什么、缓存在哪

### 问题

同一个 system prompt 反复发几百次，为什么要重复付费？

### 机制

缓存在**服务商那边**，存的是模型前向计算出来的 **KV 张量**（注意力机制里的 Key/Value 中间结果）。这部分算过一次就不用再算，直接复用。

关键限制——**按前缀做精确匹配，不是语义匹配**：

```
请求 A： [系统提示词][用户问题1]
请求 B： [系统提示词][用户问题2]
                └─ 这一段完全相同，可以命中 ─┘
```

只要开头一个字变了，后面全部作废。所以：

- 把**稳定不变的内容放最前面**：system prompt、JSON schema、术语表、few-shot 示例
- 把**每次变化的内容放最后面**：用户问题、时间戳、随机 ID、会话 id

### 两种缓存形态

| 类型 | 谁在管 | 特点 |
|---|---|---|
| 自动前缀缓存 | 推理引擎（vLLM / SGLang） | 自动生效，LRU 驱逐，通常不额外收费 |
| 显式缓存 | 平台 API | 自己创建缓存对象，设 TTL，**存储要单独计费** |

## 三、为什么自建能到 99.9%，云上只有 30%

这是很多人第一次看账单会困惑的地方。

自建（比如本地 vLLM）能做到 99.9% 命中，是因为场景几乎固定：同一个 system prompt、同一套 schema、连续会话、模型不变、时间窗内 KV 一直没被驱逐。

云端命中率低有两个原因：

1. **每次都是新数据**——会议纪要、转写文本天然不重复，前缀里塞的又都是新内容
2. **共享池会被驱逐**——你不动，别人的请求也会把你的 KV 挤出去

所以云上 30% 左右是正常的，不必当成配置错误去折腾。

### 提升命中率的实操

1. 不要在 system prompt 开头塞时间戳、随机数、请求 id
2. schema、术语表、格式说明固定成常量，永远放最前
3. 多轮会话尽量在同一个时间窗内连续跑完，别隔几小时再续
4. 批量任务用同一个前缀跑，别每批换一套提示词模板

## 四、免费额度

### 发放方式

不是"领取"，是**开通即发**：完成实名认证开通百炼后，系统自动给每个支持的模型发额度。

| 项目 | 规则 |
|---|---|
| 地域 | 仅中国内地（华北2 北京），国际站无 |
| 每个模型 | 通常 1,000,000 token |
| 有效期 | 90 天，过期不补发 |
| 归属 | 按模型独立计算，主账号 / 子账号共享同一个池 |
| 抵扣范围 | 只抵实时推理，不抵存储类费用 |
| 限制 | 同一实名主体不能再领第二次 |

控制台里那个"用完即停"开关，打开后额度耗尽会自动返回 403（`AllocationQuota.FreeTierOnly`），**不会偷偷转成付费**。想继续用就得手动关掉它。

### 1M token 能用多久

| 场景 | 估算 |
|---|---|
| 音频转写（每秒 25 token） | 1M ≈ 40,000 秒 ≈ **11 小时音频输入**，算上输出约 9~10 小时 |
| 文本整理（15 分钟会议 ≈ 8~12k token） | 1M ≈ **80~120 次整理** |
| 折成现金 | 约 1 元量级 |

注意这是**总额度，不是每天 1M**。用完就没了。

## 五、几个容易踩的计费坑

1. **schema 也是钱**——每次请求的 `response_format` 都算输入 token，200~400 token/次。量大了就是纯浪费，所以固定前置吃缓存。
2. **思考模式会翻倍**——带 thinking 的模型内部推理过程也算输出 token，不关掉的话账单可能是两倍。
3. **被截断照样收费**——`max_tokens` 设太小，输出被截断，钱一分不退。
4. **失败请求一般不计费**，但重试三次就是三倍成本，客户端要有退避而不是死循环。
5. **只看"应付金额"看不出用量**——要看账单明细里的"计费量"，0 元可能只是被免费额度抵掉了，不代表没消耗。
