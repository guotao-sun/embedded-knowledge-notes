# 长会话的上下文管理

## 一、核心矛盾

前面讲过两条几乎相反的原则：

- **缓存按最长公共前缀匹配** —— 喜欢"只增不改"，历史越多命中越长
- **上下文窗口是有限的** —— 32k 就是 32k，塞不下就得丢东西

所以两者不是二选一，分层次处理：

| 层次 | 策略 |
|---|---|
| 窗口内 | 只增不改，吃缓存 |
| 接近上限时 | 做一次"整理"，接受这一次必然的 miss |

一句话：**缓存命中率是手段，总花费最小才是目的**。偶尔一次全价重建，只要不是每轮都重建，账单就是省的。

## 二、先算预算，别靠感觉

可用输入预算 = **窗口上限 − 输出预留**。输出和输入共用窗口，不能把 32k 全给输入。

以 32k 为例：

```
总窗口            32,000
输出预留           4,000   ← 纪要可能很长，别在这里抠
─────────────────────────
输入预算          28,000
 ├─ system         2,000   （固定，永不改）
 ├─ 历史摘要区      8,000   （滚动，只追加）
 ├─ 最近原话       12,000   （最近 6~8 轮）
 └─ 新问题          1,000
```

这些配额要**写死在配置文件里**，不要靠"跑着跑着感觉快超了"。

```ini
# context_config.txt
CONTEXT_LIMIT=32768
OUTPUT_RESERVE=4000
COMPACT_THRESHOLD=0.8
KEEP_RECENT_TURNS=8
SUMMARY_MAX_CHARS=300
```

## 三、触发时机：80% 而不是 100%

```python
if estimate_tokens(history) > INPUT_BUDGET * 0.8:
    history = compact(history)
```

留 20% 缓冲的原因很实际：token 估算永远不准（中文按字数估会偏少），一旦真的超限，云端直接返回 400，这一轮白跑；本地推理可能静默截断，你还以为模型答得莫名其妙。

## 四、整理时做三件事

顺序不能反：**先归档，再压缩，最后重建**。

### 1. 归档：挪出窗口 ≠ 删除

老对话写成文件留在磁盘，以后需要回溯原文时还能取：

```
archive/2026-11-26-会议-第1段.md
```

先存后丢，否则一旦压缩丢了细节，"当时谁说的原话"就彻底没了。

### 2. 压缩：整轮合并成一条阶段小结

```python
旧原话 = history[最早若干轮]
新摘要 = llm_summarize(旧原话, "压成 300 字要点，保留人名、日期、结论")
```

注意按**整轮**删除，不要按字符截断——按字符砍会把 `tool_calls` 与 `tool` 消息的配对切断，下一次请求直接 400。

### 3. 分层：摘要也会攒爆

摘要攒多了，摘要区自己就撑满。所以摘要本身要分层：

| 层级 | 内容 | 长度上限 |
|---|---|---|
| L1 | 最近 5~8 轮原话 | 约 8k |
| L2 | 每 5 轮压一次的阶段小结 | 每条 300 字，最多留 3 条 |
| L3 | L2 的再压缩（"整场会议结论"） | 500 字，一条 |

L2 超过 3 条时，把最老的 2 条压成一条 L3。这样**总长度有界**，结构又始终是"往尾部追加"。

## 五、代价到底多大

假设每轮输入 1.5k、输入预算 28k，大约 17 轮就满：

| 策略 | 17 轮内的命中情况 | 整理次数 |
|---|---|---|
| 每轮重写摘要 | 每轮都 miss | 17 次（等于完全放弃优化） |
| 每 5 轮压一次 | 4 轮命中、1 轮 miss | 3~4 次 |
| 到 80% 再压 | 15 轮连续命中，1 轮大 miss | 1 次 |

第三种最省，代价是对预算估算的准确性要求更高。

## 六、代码骨架

```python
def maybe_compact(history, cfg):
    """history[0] 固定是 system，永不参与压缩"""
    if estimate_tokens(history) < cfg.input_budget * cfg.compact_threshold:
        return history                       # 多数轮次走这里，缓存持续命中

    old_turns = history[1:-cfg.keep_recent_turns]

    # ① 先归档
    archive_write(old_turns)

    # ② 压成一条阶段小结
    summary = llm_summarize(old_turns, cfg.summary_prompt)

    # ③ 重建（这一轮必然 miss，接受）
    return (
        [history[0]]                                        # system 原样不动
        + stored_summaries                                  # 已有阶段小结，只增不改
        + [{"role": "user", "content": f"【前情提要】{summary}"}]
        + history[-cfg.keep_recent_turns:]                  # 最近几轮原话
    )
```

关键点：

- `history[0]` 是 system，单独拎出来，它从不参与压缩
- 摘要以 `user` 消息形式追加，不要塞回 system（system 一变，整份前缀全废）
- 保留最近几轮原话，不要只留摘要——摘要必然丢细节

## 七、四个坑

1. **按 token 直接截断**——切在句子中间、破坏 role 配对，下一次请求 400。要按整轮删。
2. **只丢原文不留档**——真需要回溯时无从下手，摘要一定丢细节。
3. **压缩用的模型太弱**——摘要质量差，后面所有推理跟着歪。压缩只跑一次，值得用稍好的模型。
4. **压缩过于频繁**——每 2~3 轮压一次，等于放弃缓存还多付压缩费。

## 八、另一个问题：材料本身就超窗

前面七节讲的是"对话越聊越长"。还有一类更极端的情况：**第一句话就问一个本身就超过窗口的东西**，典型是"帮我分析整个代码工程"。

先看量级。10 万行代码按每行约 10 token 估，就是 **80 万~120 万 token**；窗口 128k。差 10 倍，任何"想办法塞进去"的路都不成立。

矛盾在这一点：

```
要判断"改这里会不会影响别处" → 得知道全貌
上下文只装得下 1%            → 看不了全貌
```

所以工业界的做法不是压缩对话，而是**换一套看材料的方式：建轻量索引、按需读片段、任务隔离、多轮循环**。

### 8.1 六个策略

| 策略 | 做什么 | 省多少 |
|---|---|---|
| 骨架视图 | 先 `ls` / `glob` 出目录树和文件名，不看内容 | 10 万行 → 几百 token |
| 检索式阅读 | `grep -n` 定位关键字，只读命中行前后几行 | 一个几千行的文件 → 几十行 |
| 符号索引 | ctags / tree-sitter / LSP（clangd、pylsp）拿函数级定义与引用 | 精确回答"谁调用了它"，不必读全文 |
| 分层摘要 | 每个文件一句话，先给地图，用时再展开 | 仓库 → 一页目录 |
| 子任务隔离 | 派子智能体各看一块，只回传结论 | 关键手段，见 8.2 |
| 压缩与外部化 | 完成步骤压成摘要；中间结果写文件，需要再读回 | 控制历史增长 |

### 8.2 子任务隔离是关键

对话历史是累积的，**读过的每个文件都留在历史里**，越读越满。所以最有效的不是压缩，而是**让不同的"上下文"彼此隔离**：

```text
主智能体：只持有"任务 + 结论 + 文件路径"
   ├─ 子任务 A：读 util/ 下 12 个文件 → 回一句"编码在 util/codec.c:120"
   ├─ 子任务 B：读 driver/ 目录     → 回一句"入口是 driver/init.c:44"
   └─ 子任务 C：grep 找调用点       → 回一句"3 处调用，见下"
```

每个子任务读完就把内容扔掉，只回传压缩后的结论。主智能体的上下文始终几千 token，但"看过"的量可以是几十万行。**这是"上下文有限、视野可以很大"的正解。**

### 8.3 工具的接口形状决定了省不省

同一份能力，接口设计不同，成本差一个数量级：

| 好接口 | 坏接口 |
|---|---|
| `read_file(path, offset, limit)` 分段读 | `read_file(path)` 返回整个文件 |
| `grep(pattern, context_lines=3)` | 把全部搜索结果全文返回 |
| `list_symbols(path)` 只给签名 | 让模型自己扫源码找函数 |

**模型只能用工具给的粒度看代码。** 工具只提供"全量"这一个档位，再聪明的模型也只能读爆上下文。

### 8.4 一次分析的实际流程

```text
1. ls / glob                → 200 个文件路径          ~2k token
2. grep 关键词              → 8 个文件、15 行命中      ~1k
3. 读 3 个关键文件            → read(offset, limit)   ~20k
4. 发现跨文件依赖            → 再 grep 符号引用        ~2k（回到第 2 步）
5. 子任务并行看两个子目录     → 只回结论               ~3k
6. 输出结论 + 关键文件清单
```

第 4 步那个回边就是 [Agent Loop](./LLM-10-智能体-运行方式与工具调用.md)：**一次不够就再查一次，每步只用最小必要信息**。只给一次机会、不给循环，大仓库基本做不了。

### 8.5 五个坑

| 坑 | 表现 | 缓解 |
|---|---|---|
| 漏读 | 只看了 3 个文件就下结论，改错地方 | 改完必须编译/跑测试，报错再回到循环 |
| 依赖追不全 | 跨目录的间接引用看不到 | 用符号索引或 grep 引用，别靠猜 |
| 编造缺失部分 | 没读到的代码模型自己补 | 明确要求它声明"这部分我没看到" |
| 摘要失真 | 分层摘要丢了关键约束 | 摘要只用于导航，动手前必须读原文 |
| 索引过期 | 改完代码索引没重建 | 每次改动后重新检索，别信旧地图 |

### 8.6 结论

**大工程分析靠"索引 + 检索 + 隔离 + 循环"，不靠更大的窗口。** 窗口从 128k 涨到 1M，只是把"要分几刀"变成"少分几刀"，策略本身不变。

## 九、什么时候可以不管这套

不是所有场景都需要。判断标准是"会话长度 × 轮次"：

- 单次问答、一次性文档处理 → 不需要，发完就结束
- 十来轮就收尾的会议纪要 → 简单滑动窗口够用，不必上分层摘要
- 需要持续几小时、上百轮的对话（陪伴、长期项目跟踪） → 才值得把这套做全

## 十、一句话结论

**窗口内只增不改吃满缓存；接近上限时归档原文、向上压一层、只重排这一次。** 缓存命中是分段策略，不是全局承诺。

窗口之外还要不要更长期的记忆、跨会话怎么"记得"，见 [长期记忆的三层设计](./LLM-07-记忆-长期记忆三层设计.md)。
