# STM32 与 Linux 的任务调度：切换时机差在哪

## 一、先说结论

两边都遵循同一句话：**在中断里"做决定"，在安全的地方"真正切换"**。差别在"安全的地方"是哪：

| | FreeRTOS（Cortex-M） | Linux（Cortex-A） |
|---|---|---|
| 谁做决定 | SysTick 里判断要不要切 | 定时器中断里判断，只置 `TIF_NEED_RESCHED` |
| 在哪真正切换 | **专门的 PendSV 中断**（软件触发，优先级最低） | **中断/系统调用返回路径**上顺手切 |
| 切换的实现 | 在 PendSV handler 里手写汇编压栈/出栈 | `__schedule()` → `context_switch()` |
| 选谁 | 优先级抢占（RRV 就绪表） | CFS 按 vruntime（见 [Linux 调度](./KERNEL-06-调度-Linux调度.md)） |

一句话记：**FreeRTOS 是"再开一个中断来切换"，Linux 是"借返回的顺风车切换"**。

## 二、FreeRTOS 的切换流程

最常见的情况：

1. **SysTick 中断**（Tick ISR）触发：累加 tick 计数
2. 检查有没有任务超时、有没有更高优先级任务就绪
3. 需要切换 → **置位 PendSV 的 pending 位**（先不切）
4. **SysTick ISR 正常退出**（此时还跑在被打断的任务上下文里）
5. **PendSV 中断**（优先级最低）随后触发：
   - 把当前任务的寄存器（R4–R11 等）压入它的任务栈
   - 栈指针存回 TCB（任务控制块）
   - 调调度器选出下一个任务
   - 取出新任务的栈指针
   - 恢复新任务的寄存器
   - 从 PendSV 返回（硬件自动恢复 R0–R3、PC、xPSR 等）

> 上下文切换完全在 PendSV Handler 里完成，切完直接退出中断，CPU 已经在跑新任务。

### 为什么非要绕 PendSV 这一道

因为 PendSV 的优先级**最低**。这意味着：只要还有别的中断在排队（比如串口、定时器），它们会先执行完，最后才轮到切换上下文。

如果直接在 SysTick 里切换，会发生两件坏事：

- 切换过程中又来了高优先级中断，现场被覆盖，回来时栈已经乱了
- 切换把"中断返回地址"改成了新任务，但当前中断的收尾工作还没做完

所以"最低优先级 + 软件触发"是一个很聪明的设计：**它把上下文切换变成一个"等所有中断都处理完才执行的收尾动作"**。

FreeRTOS 里触发它的两个 API：

```c
/* 在中断里请求切换（只打标记） */
portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
/* 在任务里主动让出 */
taskYIELD();          /* 内部就是触发 PendSV */
```

## 三、Linux 的切换流程

以定时器中断为例：

1. **Timer 中断**触发：更新 `jiffies`，调 `scheduler_tick()`
2. 如果该抢占 → 给当前进程置 `TIF_NEED_RESCHED` 标志（**只打标记**）
3. Timer 中断即将退出时（或系统调用、异常返回时）：
   - 检查 `TIF_NEED_RESCHED`
   - 置位了 → 调 `__schedule()`
4. `__schedule()` 里执行 `context_switch()`：切换 `mm_struct`、寄存器、栈
5. 切换完，从中断/异常返回到新进程的用户态或内核态

> Linux **不会在中断处理函数里直接完成上下文切换**，只打标记，在安全时机（返回路径）才真正切。

### 为什么"懒切换"

三个原因：

- **中断上下文里不能睡眠**：`__schedule()` 会阻塞当前执行流，在硬中断里做这件事本身就违规
- **关中断区间要短**：切换涉及页表、浮点状态、TLB，做在中断里会把关中断时间拉得很长
- **切换点要可控**：返回路径是一个明确的"内核即将回到用户态"的边界，在这里切最干净

## 四、中断返回路径

```text
1. 中断发生（硬件）
   → CPU 进内核模式，保存现场（寄存器、返回地址）
        ↓
2. 中断入口代码（汇编）
   → 保存更多上下文，准备调用 C 函数
        ↓
3. 执行 ISR
        ↓
4. ISR 结束
        ↓
5. 【返回路径】← 检查 TIF_NEED_RESCHED，可能在这里调度
        ↓
6. 真正退出中断（iret / eret）
   → 回到被打断的地方（用户态或内核态）
```

关键在第 5 步：**调度不是"中断干了什么"，而是"中断返回时顺手检查了一下"**。所以 IO 中断、网络中断、系统调用返回、异常返回，任何一个返回点都可能触发调度，不只是定时器。

## 五、对比表

| 特性 | STM32（FreeRTOS） | Linux |
|---|---|---|
| 切换时机 | SysTick 置位 PendSV，在 PendSV 里切 | Timer 中断置标记，在返回路径里切 |
| 切换位置 | PendSV Handler | `__schedule()` → `context_switch()` |
| 切换策略 | 优先级抢占 + 同优先级时间片轮转 | CFS 按 vruntime（普通进程） |
| 中断中切换 | 是（专门的低优先级中断） | 否（懒切换到返回路径） |
| 现场保存在哪 | 任务自己的栈 + TCB | 进程内核栈 + `thread_struct` |
| 切换开销主要花在 | 压栈/出栈寄存器 | 切页表（CR3/TTBR）、TLB、FPU 状态 |

## 六、几个容易忽略的细节

- **PendSV 优先级必须设成最低**（通常是 0xFF）。如果配高了，会出现"切换过程中被抢占 → 现场错乱"的偶发死机。
- **Linux 的返回路径分两种**：回到用户态（可以调度）、回到内核态（只有在 `preempt_count == 0` 时才能调度）。
- **内核态的长循环要主动让**：`cond_resched()` 是给"关了抢占的长循环"留的后门，不加就可能让一个 CPU 卡几百毫秒。
- **实时任务在 Linux 上也不是硬实时**：`SCHED_FIFO` 只保证"比普通进程优先"，中断延迟、关中断区间仍然存在。

## 七、常见故障对照

| 现象 | FreeRTOS 侧原因 | Linux 侧原因 |
|---|---|---|
| 偶发死机、栈错乱 | PendSV 优先级配错，或 ISR 里调了会阻塞的 API | 中断里调了睡眠函数，或关抢占太久 |
| 高优先级任务迟迟不跑 | 中断里没调 `portYIELD_FROM_ISR` | 抢占点缺失（长循环没 `cond_resched`） |
| 系统整体卡顿 | ISR 太长，PendSV 迟迟轮不到 | 软中断/工作队列堆积，或关中断区间过长 |
| 切换后外设状态错 | 切换时没保存/恢复外设上下文 | 驱动在 `suspend/resume` 里没处理状态 |

## 八、一句话总结

**决定在中断里做，切换在安全处做**：FreeRTOS 靠"最低优先级的 PendSV"把切换排到所有中断之后；Linux 靠"返回路径检查 `TIF_NEED_RESCHED`"把切换塞进返回用户态的那一刻。
