# 页表：虚拟地址是怎么变成物理地址的

## 一、先说结论

页表就是一张**"虚拟页号 → 物理页框号"的对照表**，外加一堆属性位。它解决三件事：

1. **隔离**：每个进程一张表，A 进程的地址落到物理内存哪里，B 完全不知道
2. **按需分配**：虚拟地址可以先给、物理页后补，缺了再触发缺页去拿
3. **权限与类型**：哪块可写、可执行、能不能缓存，全写在表项里

代价是每次访问都要"查表"——所以 CPU 里配了 TLB（页表缓存）来兜住热路径。

## 二、多级页表的层次

单级页表太大（32 位地址 × 4 KB 页 = 100 万个表项，光表就 4 MB），所以拆成多级，**只为真正用到的地址建子表**：

```text
页表基地址（存在 CR3 / ARM 的 TTBR0、TTBR1）
  │
  └──> 页目录（Page Directory, PD）
        ├─ PDE0 → 指向页表页框 PT0
        ├─ PDE1 → 指向页表页框 PT1
        └─ ...
              │
              └──> 页表（Page Table, PT）
                    ├─ PTE0 → 指向物理页框0（存数据）
                    ├─ PTE1 → 指向物理页框1（存数据）
                    └─ ...
```

不同架构的级数不一样：

| 架构 | 页表级数 | 基址寄存器 | 备注 |
|---|---|---|---|
| x86 / x86_64 | 2 级 / 4 级 | CR3 | 上面的图就是 x86 的两级模型 |
| ARMv7（i.MX6ULL） | 2 级 | `TTBR0`（用户）/ `TTBR1`（内核） | L1 有 4096 项，可映射 1 MB 大页（section） |
| ARMv8（RK3568） | 3~4 级 | `TTBR0_EL1` / `TTBR1_EL1` | 起始级由 TCR 配置决定 |

ARM 用**两个基址寄存器**把地址空间一分为二：低地址（用户空间）走 `TTBR0`，高地址（内核空间）走 `TTBR1`。进程切换时只换 `TTBR0`，内核映射不用重建——这也是"内核态切换进程开销小"的原因之一。

## 三、页表项里有什么

一个 PTE 不只是"物理地址"，还带着访问语义：

| 字段 | 作用 |
|---|---|
| 物理页基地址 | 真正指向的内存页（4 KB 对齐） |
| 有效位（valid） | 这一项是否可用；为 0 就是"没映射"，访问 → 缺页 |
| 权限 AP | 只读 / 读写 / 特权态可访问 |
| XN（execute never） | 是否允许取指执行（防止数据页被执行） |
| TEX / C / B | 内存类型与缓存策略：Normal（可缓存）、Device（外设，强序） |
| S（shareable） | 是否多核共享 |
| nG（not global） | 是否随进程切换失效（ASID 相关） |

**Device 类型非常关键**：外设寄存器必须映射成 Device（不缓存、强序），否则编译器/CPU 的乱序与合并会直接把寄存器访问搞乱。

## 四、4 KB 页的 PTE 结构（简化）

```text
31                        12  11          0
+---------------------------+-------------+
| 物理页基地址（20 bit）     | 属性位      |
+---------------------------+-------------+
```

- `[31:12]`：物理页框号（PFN），因为 4 KB 对齐，低 12 位永远是 0
- `[11:0]`：属性，包括上面那张表里的 XN、AP、TEX、C/B、S、nG 等
- 大页（ARMv7 的 1 MB section、ARMv8 的 2 MB block）把"物理地址位"往低位扩，少一级查表，TLB 命中率也更高

## 五、页命中：MMU 怎么翻译

![页命中](../images/image29.png)

1. 处理器给出一个虚拟地址
2. MMU 拆出虚拟页号，先查 TLB；没命中就按页表基址算出 PTE 地址，向 cache/主存取
3. cache/主存把 PTE 返回给 MMU
4. MMU 用 PTE 里的物理页框号 + 页内偏移，拼出物理地址
5. 用物理地址取数据，返回给处理器

**两次访存**是页表的固有代价（查表一次、取数据一次），所以 TLB 命中时才能接近"零成本"。TLB 一旦刷新（切页表、改映射），后续一批访问都会变慢——这就是为什么频繁 `mmap/munmap` 的程序会明显掉速。

## 六、缺页：PTE 有效位为 0 时

![缺页](../images/image30.png)

1. 处理器给出虚拟地址
2. MMU 查到 PTE
3. PTE 的**有效位是 0** → MMU 触发异常（page fault）
4. CPU 转入内核的缺页处理程序
5. 处理程序挑一个牺牲页；如果它是脏的，先写回磁盘
6. 把需要的页调入内存，更新 PTE（改成有效，填上物理页框）
7. 返回原进程，**重新执行那条导致缺页的指令**——这次 TLB/页表都能命中，正常取到数据

注意第 7 步：缺页返回后是"重试指令"，不是"跳过指令"。这也解释了为什么缺页处理必须精准恢复现场。

常见缺页类型：

| 类型 | 触发原因 | 处理 |
|---|---|---|
| 匿名页首次访问 | 申请了内存但还没给物理页 | 分配一个零页/新页 |
| 文件页未缓存 | 访问 mmap 的文件区域 | 从文件读入 page cache |
| 写时复制（COW） | fork 后子进程写共享页 | 复制一份新页 |
| 栈增长 | 越过了已映射的栈底 | 扩栈（有上限） |

## 七、被换出去的页去哪了

| 内存页类型 | 去向 |
|---|---|
| 干净文件页 | 直接丢弃（内容还在文件里，需要时重读） |
| 脏文件页 | 写回原文件后才能丢 |
| 匿名页 | 写入 swap 分区/文件 |
| 从未访问过 | 根本没分配过物理页 |

## 八、LPAE：为了 4 GB 以上的物理内存

ARMv7 默认的短描述符 PTE 只有 32 位，物理地址最多寻址 4 GB。开启 **LPAE（Large Physical Address Extension）** 之后：

- PTE 变成 **64 位（8 字节）**
- 物理地址可到 40 位（1 TB 级）
- 页表多一级（三级），权限模型更细

代价是页表占用翻倍、TLB 能装的项变少。RK3568 这类 ARMv8 平台天生就是 64 位描述符，不存在这个问题。

## 九、术语表

| 术语 | 说明 |
|---|---|
| 页表（page tables） | 虚拟地址到物理地址的对照表集合，存在主存里 |
| 页表项（PTE） | 一条具体映射：物理页框号 + 属性 |
| 页命中 | 虚拟页已在物理内存中，MMU 直接转换成功 |
| 缺页 | 虚拟页不在物理内存中（或没建立映射），触发缺页异常 |
| TLB | 页表项的硬件缓存，命中则跳过查表 |
| 页框（page frame） | 物理内存按页切分的单位，通常 4 KB |

## 十、附：DRAM 家族的分类

页表的"页"最终落在 DRAM 上，顺带把这层关系理清：

```text
DRAM（动态内存，大类）
  └── SDRAM（同步 DRAM）
        ├── SDR（单倍速）
        └── DDR（双倍速）
              ├── DDR2
              ├── DDR3
              ├── DDR4
              └── LPDDR / GDDR（低功耗 / 图形专用变种）
```

## 十一、一句话总结

页表把"虚拟页号"翻译成"物理页框号"，属性位决定能不能写、能不能执行、要不要缓存；MMU 靠 TLB 把翻译成本压下来，缺页异常则是"这张表还没填"时的兜底路径。
